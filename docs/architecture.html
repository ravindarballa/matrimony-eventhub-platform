Matrimony EventHub

A single platform where a family finds a match, then books everything the wedding needs — venue, caterer, pandit, photographer — from the same account. Nine modules, one Angular 22 shell, one NestJS API, one MongoDB cluster.

Angular 22.1.5 NestJS 12.0.1 MongoDB 7 Signals + Signal Forms AWS ECS Fargate Node 24.20.0 required

Platform overview

Indian weddings are two businesses that share a customer. Matrimony finds the match; event management spends the budget. Almost every platform picks one and treats the other as an afterthought. EventHub treats the transition between them as the product.

The commercial logic is simple: matrimony acquires users cheaply and holds them for months, but monetises weakly (subscription only). Event booking monetises strongly (8–15% commission on a ₹8–40 lakh wedding) but has brutal customer-acquisition costs. Running both means the acquisition cost of the second business is already paid by the first.

That shapes the architecture. The moment of conversion — a matrimony profile moving to status: 'engaged' — is a domain event, not a database update. It fans out to the event module (create a draft wedding project), the notification module (vendor discovery campaign), and reporting (the funnel metric the business is actually run on). Every module below is built so that this handoff is first-class rather than bolted on.

Design rule

Roles gate routes. Ownership gates records. A VENDOR_OWNER may reach /vendor/bookings/:id because of their role, but the API returns that booking only if booking.vendorId is in their org. Never rely on the route guard for data authorisation — the guard is UX, the server check is security.

System architecture

One Angular application, lazy-loaded per module. One NestJS API, modular monolith. One MongoDB replica set. Asynchronous work leaves the request path through SQS; nothing that a user waits on depends on a queue.

Why a modular monolith

The temptation with nine modules is nine services. Resist it at this size. A wedding booking touches events, vendors, payments and notifications in one user action; as a monolith that is a single MongoDB transaction, and as microservices it is a saga with compensating transactions, a distributed trace, and an on-call rotation. The module boundaries below are real — enforced by ESLint import rules and by the fact that modules talk through events and injected service interfaces, never by reaching into each other's schemas — so the option to extract stays open. Extract when a module needs independent scaling, not when the org chart suggests it.

AUTH

Authentication Module

Identity, sessions, roles and account recovery for all six personas. Every other module assumes this one is correct.

Business requirements

  • Phone-first registration. In the Indian market the mobile number is the identity. Email is optional at signup and required only before a payout. OTP over SMS is the primary factor.
  • One account, many roles. A user who registers as a seeker and later books a caterer must not create a second account. Roles are added to the existing identity.
  • Vendor accounts are provisional until verified. A VENDOR_OWNER can sign up and build a listing immediately but cannot receive bookings or money until KYC clears.
  • Support impersonation, fully audited. Ops must be able to see what a user sees to resolve a dispute, with every impersonated session written to an immutable audit log and capped at 30 minutes.
  • Session revocation. A user can see active devices and sign out of any of them; an admin can revoke every session for an account instantly.
  • Regulatory. Passwords never logged, OTPs never returned in a response body, DPDP-compliant consent captured at registration with a timestamp and version.

User stories

  • AUTH-01As a visitor, I register with my mobile number and an OTP so I can start building a profile without inventing a password.
  • AUTH-02As a returning user, I sign in with mobile + password, or mobile + OTP if I have forgotten it, so I am never locked out.
  • AUTH-03As a seeker who just got engaged, I add the customer role to my existing account so my wedding bookings sit under the same login.
  • AUTH-04As a vendor owner, I register my business and upload PAN and GSTIN so I can be verified and start quoting.
  • AUTH-05As a user, I see every device signed into my account and revoke any of them, so a shared family laptop is not a permanent risk.
  • AUTH-06As support, I impersonate a customer to reproduce a booking failure, and the platform records that I did.
  • AUTH-07As an admin, I lock an account and kill its sessions immediately when fraud is reported.

Service layer design

Two objects, sharply separated. AuthApi knows HTTP and nothing else. AuthStore knows session state and nothing about URLs. This is the only module where a SignalStore is provided in root — the session is genuinely global.

// features/auth/data/auth.store.ts
export const AuthStore = signalStore(
  { providedIn: 'root' },
  withState<AuthState>({
    user: null, accessToken: null, status: 'idle', impersonator: null,
  }),
  withComputed(({ user, impersonator }) => ({
    isAuthenticated: computed(() => !!user()),
    roles:           computed(() => user()?.roles ?? []),
    isVendor:        computed(() => (user()?.roles ?? []).includes('VENDOR_OWNER')),
    // vendors see a restricted shell until KYC clears
    vendorVerified:  computed(() => user()?.vendor?.kycStatus === 'VERIFIED'),
    isImpersonating: computed(() => !!impersonator()),
  })),
  withMethods((store, api = inject(AuthApi), router = inject(Router)) => ({
    async login(dto: LoginDto) {
      patchState(store, { status: 'loading' });
      const res = await firstValueFrom(api.login(dto));
      patchState(store, { user: res.user, accessToken: res.accessToken, status: 'idle' });
      router.navigateByUrl(landingRouteFor(res.user.roles));
    },
    async logout() {
      await firstValueFrom(api.logout());   // clears the refresh cookie server-side
      patchState(store, { user: null, accessToken: null, impersonator: null });
      router.navigateByUrl('/auth/login');
    },
    setSession: (user: SessionUser, accessToken: string) =>
      patchState(store, { user, accessToken }),
  })),
);

State management strategy

Store, root
AuthStore — the only truly global state on the platform. Read by the app shell, every guard, and the HTTP interceptor.
Access token
Held in memory only, inside the store. Never localStorage — an XSS in any third-party script would otherwise walk away with it.
Refresh token
httpOnly; Secure; SameSite=Strict cookie, scoped to /api/v1/auth. JavaScript cannot read it, so the SPA calls POST /auth/refresh and trusts the browser to attach it.
Rehydration
provideAppInitializer calls /auth/refresh once at bootstrap. A hard refresh restores the session from the cookie before the first route resolves, so no page flashes the logged-out state.
Component state
OTP countdown, password visibility, stepper index — plain signal(), discarded with the component.

export const roleGuard = (...allowed: Role[]): CanActivateFn => () => {
  const auth   = inject(AuthStore);
  const router = inject(Router);
  if (!auth.isAuthenticated()) {
    return new RedirectCommand(router.parseUrl('/auth/login'));
  }

    ? true
    : new RedirectCommand(router.parseUrl('/403'));

Two interceptors carry the whole integration. authInterceptor attaches the bearer token and skips public URLs; refreshInterceptor catches a 401, refreshes once, and replays every request that queued behind it.

// core/interceptors/refresh.interceptor.ts
let refresh$: Observable<string> | null = null;   // module-scoped: one flight, shared

export const refreshInterceptor: HttpInterceptorFn = (req, next) => {
  const store = inject(AuthStore);
  return next(req).pipe(
    catchError((err: HttpErrorResponse) => {
      if (err.status !== 401 || req.url.includes('/auth/')) return throwError(() => err);

      refresh$ ??= inject(AuthApi).refresh().pipe(
        tap(res => store.setSession(res.user, res.accessToken)),
        map(res => res.accessToken),
        finalize(() => { refresh$ = null; }),   // release the gate either way
        shareReplay({ bufferSize: 1, refCount: true }),
      );

      return refresh$.pipe(
        switchMap(token => next(req.clone({
          setHeaders: { Authorization: `Bearer ${token}` },
        }))),
        catchError(() => { store.logout(); return throwError(() => err); }),
      );
    }),
  );
};
Why this shape matters

A dashboard fires six parallel requests. Without the shared refresh$, an expired token produces six refresh calls, five of which present an already-rotated token — and with reuse detection enabled, that revokes the user's entire session family and logs them out. The single-flight gate is not an optimisation, it is a correctness requirement.

Validation strategy

One schema, two consumers. The Signal Forms schema on the client and the class-validator DTO on the server encode the same rules; the client's job is speed of feedback, the server's is truth.

MAT

Matrimony Module

Profiles, partner preferences, match scoring, horoscope compatibility, interests and conversation. The acquisition engine.

Business requirements

  • Profiles are often managed by a parent. profileManagedBy distinguishes SELF from PARENT, SIBLING, RELATIVE — this changes the tone of notifications and who the contact number belongs to.
  • Photo privacy is the retention lever. Four visibility modes: public, members-only, on-request, and blurred-until-mutual-interest. Families will not upload otherwise.
  • Horoscope matching is not optional. Ashtakoota (36-guna) scoring and Mangal Dosha detection are table stakes; a platform without them loses a large share of the market outright.
  • Interest is a two-sided state machine. Sent → accepted/declined; contact details unlock only on mutual acceptance. This is the core paywall.
  • Free tier sees, paid tier speaks. Free users browse and receive; sending interest beyond a daily quota and initiating chat require a subscription.
  • Safety. Report/block, photo moderation before publication, and a hard rule that a blocked user disappears from search both ways.
  • The conversion hook. Marking a profile engaged triggers the event-module handoff. This is the single most valuable action on the platform.

User stories

  • MAT-01As a parent, I create a profile for my daughter and mark that I manage it, so matches know who they are speaking to.
  • MAT-02As a seeker, I set partner preferences — age, height, community, education, city, diet — and see how many profiles currently match before I save.
  • MAT-03As a seeker, I filter search by gotra exclusion so I never see profiles my family cannot consider.
  • MAT-04As a seeker, I view a guna score out of 36 against any profile and see the eight koota breakdown, so I know why it scored that way.
  • MAT-05As a seeker, I keep my photos blurred until interest is mutual, so my picture is not circulating.
  • MAT-06As a seeker, I send an interest and see its state clearly, so I am not guessing whether it was delivered.
  • MAT-07As a free user, I see that contact details are locked and exactly what a plan unlocks, so the upgrade is an informed choice.
  • MAT-08As a seeker, I block a profile and never encounter it again in any surface.
  • MAT-09As a newly engaged user, I mark my profile engaged and am offered wedding vendors in my city.

Service layer design

Search is the interesting case, and it is where httpResource earns its place. Filters are signals; the request is a function of those signals; changing any filter re-fetches automatically with no subscription, no switchMap, and no manual loading flag.

// features/matrimony/data/matrimony-api.ts
@Injectable({ providedIn: 'root' })
export class MatrimonyApi {
  private base = '/api/v1/matrimony';

  /** Reactive search: re-runs whenever `filters` or `page` change. */
  searchResource(filters: Signal<SearchFilters>, page: Signal<number>) {
    return httpResource<Paged<ProfileSummary>>(() => ({
      url: `${this.base}/profiles/search`,
      method: 'POST',
      body: { ...filters(), page: page(), limit: 20 },
    }), { defaultValue: { items: [], total: 0, page: 1 } });
  }

  gunaScore(profileId: string) {
    return httpResource<GunaResult>(() => `${this.base}/profiles/${profileId}/guna`);
  }
}
// the page composes it — note there is no subscribe() and no ngOnInit
export class SearchPage {
  private api = inject(MatrimonyApi);
  protected store = inject(SearchStore);          // filters live here, survive back-nav

  page = signal(1);
  results = this.api.searchResource(this.store.filters, this.page);

Event Booking Module

Wedding projects, vendor discovery, quotes, availability, and the booking state machine. Where the money is made.

Business requirements

  • A wedding is a project, not a booking. One Indian wedding is 3–6 functions (mehendi, haldi, sangeet, ceremony, reception) across 2–4 days, each with its own venue, guest count and vendor set. The aggregate root is the wedding; bookings hang off its functions.
  • Quote-first, not cart-first. Wedding services are negotiated. The flow is enquiry → vendor quote → optional counter → acceptance → booking. A fixed-price "add to cart" model does not survive contact with this market.
  • Availability is a hard constraint. A venue on 14 February is a single unit of inventory. Double-booking is the one failure that cannot be apologised away, so acceptance takes a transactional slot lock.
  • Muhurat dates concentrate demand. A handful of auspicious dates carry a large share of annual bookings. Search must surface availability against those dates first, and the system must survive the load spike when they are announced.
  • Budget tracking. Customers set a total budget and per-category allocation, and must see committed vs. remaining at all times.
  • Cancellation is tiered by proximity. Refund percentage is a function of days-to-event, defined per vendor within platform bounds, and shown before the customer confirms.

// server: quote acceptance is the one place double-booking can occur.
// A unique partial index on (vendorId, date) where status is active makes
// the race impossible at the storage layer, not merely unlikely.
async acceptQuote(quoteId: string, customerId: string) {
  const session = await this.conn.startSession();
  try {
    return await session.withTransaction(async () => {
      const quote = await this.quotes.findById(quoteId).session(session);
      if (quote.validUntil < new Date()) throw new GoneException('EVT_QUOTE_EXPIRED');

      // throws E11000 on collision → mapped to 409 EVT_SLOT_TAKEN
      await this.slots.create([{
        vendorId: quote.vendorId, date: quote.functionDate, status: 'HELD',
      }], { session });

      const booking = await this.bookings.create([{ ...toBooking(quote), status: 'ACCEPTED' }], { session });
      await this.quotes.updateOne({ _id: quoteId }, { status: 'ACCEPTED' }, { session });
      return booking[0];
    });
  } finally { await session.endSession(); }
}

VND

Vendor Portal

The supply side: onboarding, KYC, service catalogue, calendar, quoting, and payouts. Vendors are the platform's inventory.

Business requirements

  • Nine categories, different shapes. Venues price per-day with capacity; caterers price per-plate with menu tiers; photographers price per-package with deliverables; pandits price per-ritual. A single rigid pricing model will not fit — the catalogue uses a discriminated union on category.
  • KYC gates money, not presence. A vendor lists and builds a portfolio immediately; verification is required before accepting a booking or receiving a payout. PAN and bank proof are mandatory, GSTIN is required above the ₹20 lakh turnover threshold.
  • Calendar is the critical surface. Vendors must block dates for offline bookings, personal leave and travel buffers. An out-of-date calendar produces the double-booking the platform exists to prevent.
  • Response time is a ranking input. Median time-to-quote directly affects search position; vendors must see their own number and how it compares.
  • Payouts are scheduled, not instant. Advance releases T+2 after the event date, balance T+7 after customer sign-off, minus commission and TDS. Vendors need a clear ledger.
  • Staff delegation. An owner invites staff who can quote and manage the calendar but can never see bank details or trigger payouts.

  • VND-01As a vendor owner, I complete KYC in one sitting and see exactly which document is holding up my verification.
  • VND-02As a caterer, I define per-plate packages with menu tiers and minimum guest counts, because that is how my business actually prices.
  • VND-03As a venue owner, I block dates already booked offline so the platform never sells them.
  • VND-04As a vendor, I get a push notification for a new enquiry and respond with an itemised quote in under two minutes.
  • VND-05As a vendor, I see my earnings ledger — booked, released, pending, TDS deducted — so I can reconcile against my bank.
  • VND-06As a vendor owner, I invite my booking manager as staff without giving them access to my bank account.
  • VND-07As a vendor, I see my median response time and conversion rate, so I know why my ranking moved.

Business requirements

PAY

Payment Module

Milestone collection, escrow, commission, refunds, vendor payouts and subscriptions. The module where a bug costs real money.

Business requirements

  • Milestone payments, not one-shot. A booking is collected as an advance (10–50% at acceptance) and a balance (due 7 days before the event). Large bookings may add a third instalment.
  • The platform holds funds. Money sits with the platform between collection and payout, so the customer has recourse and the vendor has certainty. Advance releases T+2 after the event, balance T+7 after sign-off.
  • Commission and TDS at source. Platform commission (8–15% by category) and 1% TDS under section 194-O are deducted at payout, with both lines visible in the vendor's ledger.
  • Refunds are tiered and automatic. The refund percentage follows days-to-event; the customer sees the exact figure before confirming, and it is computed server-side only.
  • Subscriptions are separate. Matrimony plans are recurring and must never share code paths with booking payments — different lifecycle, different failure modes, different reconciliation.
  • Idempotency is non-negotiable. Every write carries an idempotency key. A retried request must never charge twice.
  • Reconciliation daily. An automated job matches gateway settlements against internal ledger entries and raises a discrepancy alert. Money that does not reconcile is an incident.

User stories

  • PAY-01As a customer, I pay the advance by UPI and my booking is confirmed within seconds.
  • PAY-02As a customer, I see a payment schedule with due dates and get reminded before the balance falls due.
  • PAY-03As a customer, I see the exact refund amount before I confirm a cancellation, with the deduction explained.
  • PAY-04As a vendor, I see when each payout lands and what was deducted, so I can reconcile with my bank.
  • PAY-05As a seeker, I subscribe to a matrimony plan and it renews without my intervention until I cancel.
  • PAY-06As finance, I export a GST-compliant invoice register for a period.
  • PAY-07As a customer whose payment failed mid-flow, I retry without losing my booking or being charged twice.

Service layer & state management

No store
Deliberate. Payment state is authoritative on the server; caching it client-side invites showing a stale "paid" to someone who was not charged.
Component signals
A single status signal drives the checkout screen: 'idle' | 'creating' | 'gateway' | 'verifying' | 'success' | 'failed'. The template is one @switch over it.
Status polling
After the gateway returns, poll GET /payments/:id every 2 s for up to 30 s while the webhook lands. Then show "we're confirming your payment" with a reference number — never a failure, because the money may well have moved.
Idempotency key
A UUID generated when the checkout page mounts, reused across every retry from that page. Retrying is then provably safe.
export class CheckoutPage {
  intent = input.required<PaymentIntent>();
  status = signal<CheckoutStatus>('idle');
  private idempotencyKey = crypto.randomUUID();   // stable for this page instance

  async pay() {
    this.status.set('gateway');
    const result = await this.checkout.open(this.intent());
    if (result.kind === 'dismissed') { this.status.set('idle'); return; }

    // the gateway said yes; the server has not confirmed yet
    this.status.set('verifying');
    const confirmed = await this.api.pollUntilSettled(result.paymentId, { timeoutMs: 30_000 });
    this.status.set(confirmed ? 'success' : 'pending');
  }
}

The money model

Store money as integer paisa. Never as a float.

0.1 + 0.2 !== 0.3 in IEEE-754, and a wedding booking is six figures. Every amount on this platform is a number of paisa (₹1 = 100 paisa), typed as Paisa via a branded type so a rupee value cannot be assigned to it by accident. Formatting to ₹ happens only at the display edge, in one pipe. Razorpay's API also takes paisa, so there is exactly one conversion boundary in the system — the UI.

export type Paisa = number & { readonly __brand: 'Paisa' };

export const COMMISSION_BPS: Record<VendorCategory, number> = {
  VENUE: 800, CATERING: 1000, PHOTOGRAPHY: 1200, DECOR: 1200,
  MAKEUP: 1500, MUSIC: 1200, PANDIT: 800, TRANSPORT: 1000, INVITATION: 1500,
};  // basis points — integer arithmetic throughout, no rounding drift

export function splitPayment(gross: Paisa, category: VendorCategory) {
  const commission = Math.round(gross * COMMISSION_BPS[category] / 10_000) as Paisa;
  const tds        = Math.round(gross * 100 / 10_000) as Paisa;   // 1% u/s 194-O
  const vendorNet  = (gross - commission - tds) as Paisa;
  return { gross, commission, tds, vendorNet };   // always sums exactly to gross
}

// server: webhook handler — verify, then deduplicate, then act
@Post('webhook')
@Public()
async handle(@Req() req: RawBodyRequest<Request>, @Headers('x-razorpay-signature') sig: string) {
  // 1. verify against the RAW body — a parsed-and-restringified body will not match
  const expected = createHmac('sha256', this.cfg.webhookSecret)
    .update(req.rawBody!).digest('hex');
  if (!timingSafeEqual(Buffer.from(sig), Buffer.from(expected))) {
    throw new UnauthorizedException('PAY_BAD_SIGNATURE');
  }

  const event = JSON.parse(req.rawBody!.toString());

  // 2. deduplicate — gateways retry, and they retry aggressively
  const fresh = await this.webhookLog.tryInsert(event.id);   // unique index on event.id
  if (!fresh) return { received: true };                   // already handled, still 200

  // 3. act inside a transaction; always 200 so the gateway stops retrying
  await this.payments.applyWebhook(event);
  return { received: true };
}

NTF

Notification Module

Four channels, one template registry, one preference model. Entirely event-driven — no other module calls it directly.

Business requirements

  • Four channels. In-app (always), push (web push), SMS (transactional, DLT-registered), email (SES), WhatsApp (the highest-engagement channel in this market, via a BSP).
  • Channel by urgency, not by preference alone. A new interest is in-app and push. A payment due tomorrow is SMS and WhatsApp. A booking confirmation is all four. Criticality is a property of the template, and critical transactional messages ignore marketing opt-outs.
  • DLT compliance. Indian SMS requires pre-registered templates and header IDs under TRAI DLT rules. Template IDs are configuration, not code, and an unregistered send must fail loudly in staging.
  • Quiet hours. Nothing non-critical between 22:00 and 08:00 IST — queued and released at 08:00.
  • Deduplication. Five interests in ten minutes is one digest, not five pings.
  • Full auditability. Every send is logged with channel, template, provider message id and delivery status, for both debugging and compliance.

User stories

  • NTF-01As a seeker, I am notified the moment someone accepts my interest, because that is time-sensitive.
  • NTF-02As a vendor, I get a WhatsApp message for a new enquiry, because I do not sit in the portal all day.
  • NTF-03As a customer, I am reminded three days before a payment is due, on a channel I will actually see.
  • NTF-04As a user, I turn off marketing messages per channel and it is respected immediately.
  • NTF-05As a user, I am not woken at 2 a.m. by a profile view.
  • NTF-06As support, I look up whether a notification was actually delivered when a user says they never got it.

Architecture

This module is a consumer, never a caller. Other modules emit domain events; the notification module subscribes. That inversion is what keeps it removable — deleting it would break no other module's compilation.

RPT

Reporting Module

Operational dashboards, financial reconciliation, vendor performance, and the matrimony→events funnel the business is actually steered by.

Business requirements

  • Three audiences, three depths. Vendors see their own performance; admins see platform health; finance sees reconciliation and GST. Same pipeline, different projections and different authorisation.

402Payment required — subscription quota exhausted, or a gateway decline.

Conventions

  • Pagination. Offset (?page=&limit=) for bounded admin lists; cursor (?cursor=) for feeds and queues, which grow while being read.
  • Filtering. Query params for simple reads; POST /search where the filter object is large — matrimony and vendor search both use it.
  • Partial update. PATCH with a partial body. PUT only for genuine whole-resource replacement (preferences, availability ranges).
  • Idempotency. Idempotency-Key required on every payment write, honoured for 24 hours.
  • Rate limits. 100 req/min authenticated, 20 req/min anonymous, 5 req/min on OTP endpoints — per IP and per identity.
  • Swagger. Generated from decorators, served at /api/docs, protected by basic auth outside development.

NestJS 12 is ESM-only — verified against the shipped package

@nestjs/common@12 declares "type": "module" and ships no CommonJS build, so the API is ESM throughout: module: nodenext, and every relative import carries an explicit .js extension — ./auth.service.js, written that way inside a .ts file. Two consequences bite immediately. Type-only imports from CommonJS dependencies such as Mongoose must use import type, or Node throws "Named export 'Connection' not found" at load. And Jest must run under --experimental-vm-modules, where the jest global is not injected — set testTimeout in config rather than calling jest.setTimeout().

@nestjs/throttler has no NestJS 12 release

Its latest published version (6.5.0) is CommonJS and peers at @nestjs/common ^11, so it cannot be used here. The platform ships a small replacement at core/throttle/throttle.guard.ts with the same @Throttle({ limit, ttlMs }) ergonomics and a swappable store. Its default store is in-memory and therefore per-process. That is correct for local development and a single task, and wrong the moment the service scales to two — each task would enforce its own separate quota, multiplying the effective limit by the task count. Move it to the Redis store before the first production deploy; this is the one piece of scaffolding that is a genuine liability if left as-is.

Folder structure

One repository, two applications, plus shared TypeScript contracts. Separate package manifests, no workspace tooling — no Nx, no Lerna, no monorepo framework, in line with the constraints. packages/contracts is consumed as an ordinary npm file: dependency (@eventhub/contracts), which is plain npm rather than a workspace tool.

Why a file: dependency and not a TypeScript path alias

A path alias looks tidier and fails at runtime. TypeScript does not rewrite module specifiers, so under ESM an aliased @contracts is emitted verbatim and Node cannot resolve it; pointing the alias at index.ts instead emits a .ts path that Node also cannot load, and pointing it at the directory emits a directory specifier, which ESM does not resolve either. A real package with an exports map sidesteps all three — resolution becomes ordinary node_modules lookup, and the build order is simply "contracts first".

Why packages/contracts is worth the indirection

Enums like BookingStatus, VendorCategory and Role, and the shape of every DTO, are defined once and imported by both applications through a tsconfig path alias. Without it, the two sides drift: the API renames a status, the client keeps comparing against the old string, and nothing fails until runtime. With it, the rename is a compile error in the client — which is exactly where you want to find out. This is a shared folder and a path mapping, not a workspace tool, so it adds no build orchestration.

Security architecture

This platform holds three things worth stealing: identity documents, private family data, and money in transit. The controls below are grouped by what they protect.

Authentication & tokens

Authorisation

Three layers, each of which must independently pass. Skipping any one of them is the bug class that produces a breach.

  1. Route guard (client). UX only. Hides what the user cannot use. Provides no security whatsoever and is never counted as a control.
  2. Role guard (server). RolesGuard reads @Roles() metadata against the JWT. Admin endpoints re-read roles from the database rather than trusting the token, so a token minted before a demotion cannot be replayed.
  3. Ownership check (server, in the service). Every read and write of a user-owned record filters on the caller's id at the query level, not with a post-fetch if.
// Correct: ownership is part of the query. A wrong id returns nothing.
const booking = await this.bookings.findOne({ _id: id, customerId: user.sub });
if (!booking) throw new NotFoundException();

// Wrong: the record is loaded before the check. Timing and error-shape
// differences leak existence, and one forgotten `if` exposes every booking.
const booking = await this.bookings.findById(id);
if (booking.customerId !== user.sub) throw new ForbiddenException();

On ApproximateNumberOfMessagesVisible. Scales to zero out of hours; wedding-season bursts are absorbed by the queue rather than by the API.

Auspicious dates are known in advance. Scheduled scaling raises the minimum task count for those windows — reactive autoscaling alone reacts too late for a predictable spike.

Atlas M30 with auto-scaling storage; reads that tolerate staleness use secondaryPreferred; PITR with a 7-day window.

Deployment strategy

API
ECS rolling update, 200% max / 100% min healthy, so capacity never dips. ALB health check at /health/ready; automatic rollback on alarm.
Web
Build once, push to S3 with hashed filenames and long cache headers; index.html is no-cache. CloudFront invalidation limited to /index.html — invalidating /* is slow and needless with hashed assets.
Migrations
Run as a one-off ECS task before the service update. Every migration is forward-only, idempotent, and additive — no destructive change ships in the same release as the code that stops using the field.
Expand/contract
Renaming a field is three releases: add the new field and dual-write; backfill and switch reads; drop the old field. This is what makes a rollback survivable.
Feature flags
Server-evaluated, delivered in the session payload. Risky work merges dark rather than living on a long branch.
Rollback
Re-deploy the previous task definition — under two minutes. Because migrations are additive, code rollback never requires a data rollback.

Three decisions to revisit before they calcify

The monolith. Extract when a module needs independent scaling or an independent release cadence — not when the team grows. The boundaries are already drawn; the trigger is operational, not organisational.

Denormalised vendor ratings. vendors.rating is recomputed on write because search sorts on it. If review volume makes that write path hot, move to a periodic recompute and accept eventual consistency on a number nobody reads to two decimal places.

Roles as a flat array. Six roles fit in an array on the user document. The moment vendor organisations need per-resource permissions for staff, this becomes a permissions table — plan that migration before writing the twentieth roles.includes() check.
